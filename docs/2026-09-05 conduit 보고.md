## 3. 렌즈에 걸린 것

### ① 읽기 실패를 "비어 있음"으로 갈음하고, 그 값을 다시 쓴다 — 조용한 오답

```python
def _load_history():
    try:
        return json.loads(HISTORY_FILE.read_text(encoding="utf-8"))
    except Exception:
        return []                      # yt2text.py:261-265
```

`history_add()`는 같은 락 안에서 이 값을 받아 항목을 얹고 그대로 저장한다
(`yt2text.py:358` → `:367`). 읽기가 한 번 실패하면 `entries`는 `[]`가 되고,
바로 뒤 `_save_history()`가 **방금 뽑은 한 건만 남기고 히스토리 전체를 덮어쓴다.**
`_load_folders()`/`_save_folders()`도 같은 모양이다(`:595-599`, `:634-644`, `:658-669`).

이게 렌즈에 걸리는 이유는 손실 자체가 아니라 **손실이 정상 상태와 구별되지 않는다**는
점이다. 빈 히스토리는 "아직 아무것도 안 뽑은 사용자"와 화면상 똑같고, 예외도 로그도
남지 않는다. `_atomic_write()`가 쓰기 도중 파손은 이미 막아 두었으니 남은 입구는
권한·인코딩·수동 편집으로 깨진 JSON인데, 그 경우 복구가 아니라 완전 삭제로 간다.

→ **대신:** 읽기 실패와 "파일 없음"을 다른 값으로 돌려주고, 실패면 쓰기 경로를 막는다
(fail-closed). 파일이 없을 때만 `[]`가 정상이다.

### ② 길이를 못 읽으면 OOM 경로로 떨어진다 — 조용한 오답

```python
duration = info.get("duration") or 0   # yt2text.py:947
...
if duration and duration > CHUNK_SEC * 1.5:   # 긴 영상 분할
```

바로 위 주석이 스스로 적어 둔 대로, 분할을 안 타면 통짜 디코딩이 **7시간 영상 기준
~10GB**를 먹고 OOM으로 죽는다. yt-dlp가 `duration`을 안 주면 `0`이 되고, `0`은
"짧은 영상"과 구별되지 않아 분할이 조용히 꺼진다. 결측이 정상 범위 안으로 접히는
전형이다.

→ **대신:** `None`을 유지하고, 길이를 모르면 분할을 **켠 채로** 가거나
`_ffprobe_duration()`(이미 있다)으로 한 번 더 확인한다.

### ③ 경미 — 표시·정렬만 흔들림

`it["dur"] or 0`(`:225`, `:242`, `:254`, `:809`)은 문단 분리 간격과 SRT 끝시각을,
`c.get("like_count") or 0`(`:428`)은 댓글 정렬 순서를 어긋나게 한다. 데이터가 사라지진
않아 위 둘과 같은 급으로 다루지 않는다.

### 적발 아님 (판단 근거를 남겨 둔다)

썸네일 캐시(`:331`), `_ffprobe_duration`(`:853`, `None` 반환 후 호출부에서 검사),
`_saved_ts`(`:377`, `None`이면 "안 지움"이 문서화된 안전한 쪽), CUDA 프리로드(`:869`)의
예외 삼킴은 전부 부가 기능이고 실패해도 본 경로의 값이 바뀌지 않는다.

## 5. 킷에 되먹일 후보

③번 렌즈에 새로 걸린 모양 하나. 킷에 이미 같은 문장이 있으면 링크로 대체한다.

> **읽기 실패를 빈 값으로 갈음한 뒤 그 값을 다시 쓰지 마라.**
> 증상: 로드 실패 → `[]`/`{}` → 같은 트랜잭션에서 저장 → 원본 소실.
> 왜 안 보이나: 빈 상태가 "아직 안 만든 상태"와 화면상 동일해 예외도 알림도 없다.
> → 대신: "없음"과 "못 읽음"을 다른 값으로 돌려주고, 못 읽었으면 쓰기를 막는다.
